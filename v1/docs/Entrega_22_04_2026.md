## 1. Retirar el manejo de localStorage para adjuntos

### Contexto

El 21/04/2026 se introdujo un sistema de caché en `localStorage` para gestionar la disponibilidad de archivos adjuntos. Dicho sistema incluía las funciones `adjCacheInit`, `adjCacheClear`, `adjCacheGet`, `adjCacheSet` y la verificación en background `_adjuntoVerificar` (fetch HEAD), con el objetivo de evitar mostrar links de archivos rotos.

Tras trabajo conjunto con el equipo cloud se identificó que la causa raíz de la intermitencia **no era la persistencia de los links en el navegador** sino la arquitectura multi-réplica del clúster de Kubernetes: los archivos físicos se almacenaban en el sistema de archivos local de cada pod, y el `fetch HEAD` del cliente podía llegar —vía load balancer— a una réplica diferente a la que tenía el archivo, generando falsos negativos que se persistían en `localStorage`.

### Decisión

Se definió en conjunto:

1. **Cloud** configura el servicio de Kubernetes para operar con **un solo pod activo** (sin réplicas). Esto elimina la causa raíz de la intermitencia.
2. **Desarrollo** retira completamente el sistema de caché de `localStorage` para adjuntos, que ya no aporta valor y añadía complejidad innecesaria.
3. **Desarrollo** agrega un scheduler de limpieza periódica de la carpeta `uploads/files/{idChat}-{remitente}` para controlar el espacio en disco (ver Punto 2).

## 2. Control uploads — Scheduler de limpieza de adjuntos

### Descripción

Se creó un nuevo scheduler que recorre periódicamente la carpeta `uploads/files/` y elimina los archivos adjuntos de cada chat que superen el número de días configurado en la variable de entorno `TIEMPO_VIDA_ADJUNTOS`.

Si al procesar una carpeta `{idChat}-{remitente}` todos sus archivos fueron eliminados, la carpeta completa también se borra para evitar acumulación de directorios vacíos.

### Nueva variable en `.env` / `.env.example`

| Variable | Tipo | Descripción | Ejemplo |
|---|---|---|---|
| `TIEMPO_VIDA_ADJUNTOS` | `integer` (días) | Número de días de vida de los adjuntos. Archivos más antiguos se eliminan. | `30` |
| `CRON_LIMPIEZA_ADJUNTOS` | `string` (cron) | Expresión cron que define la frecuencia de ejecución. Valor por defecto si se omite: `0 3 * * *` (3:00 a.m. diario). | `0 3 * * *` |

### Archivo creado: `v1/schedulers/limpiezaAdjuntos.scheduler.js`

#### Flujo de ejecución

```
Al iniciar el servidor (delay 5s):
  └─ ejecutarLimpieza()

En cada ejecución programada (CRON_LIMPIEZA_ADJUNTOS):
  └─ ejecutarLimpieza()
       ├─ Lee uploads/files/ → lista de carpetas {idChat}-{remitente}
       ├─ Por cada carpeta:
       │    ├─ Revisa subcarpetas received/ y send/
       │    ├─ Por cada archivo (excluye .gitkeep):
       │    │    └─ Si (ahora - mtime) > TIEMPO_VIDA_ADJUNTOS días → fs.unlinkSync()
       │    └─ Si todos los archivos fueron eliminados → fs.rmSync(carpeta, recursive)
       └─ Registra en log: carpetasRevisadas, archivosEliminados, carpetasEliminadas, errores
```

#### Lógica de antigüedad

La antigüedad de un archivo se calcula usando `fs.statSync().birthtimeMs` (fecha de creación). En sistemas Linux donde `birthtime` no está disponible el kernel retorna `0`, por lo que en ese caso se usa `mtimeMs` como respaldo.

Un archivo es candidato a eliminación cuando su edad es **mayor o igual** al límite configurado:

```
(Date.now() - archivo.creadoMs) >= (TIEMPO_VIDA_ADJUNTOS × 86_400_000 ms)
```

Ejemplo: con `TIEMPO_VIDA_ADJUNTOS=30`, un archivo creado hace exactamente 30 días o más es eliminado.

#### Frecuencia de ejecución

El scheduler corre **una sola vez al día** a la hora definida en `CRON_LIMPIEZA_ADJUNTOS`. No se ejecuta al arrancar el servidor. El valor por defecto es `0 3 * * *` (3:00 a.m. diario).

#### Registro en logs

Cada ejecución registra los eventos a través del logger centralizado del proyecto con el contexto `scheduler` / recurso `limpiezaAdjuntos.*`. Los campos registrados son:

- `carpetasRevisadas`: total de carpetas `{idChat}-{remitente}` inspeccionadas.
- `archivosEliminados`: cantidad de archivos borrados en esa ejecución.
- `carpetasEliminadas`: carpetas de chat eliminadas por quedar completamente vacías.
- `totalErrores`: errores no fatales durante el proceso (archivo en uso, permisos, etc.).

### Registro en `v1/app.js`

El scheduler se registra en el bloque de inicialización de schedulers al levantar el servidor, con el mismo patrón de try/catch que los schedulers existentes.
