## 1. Corrección error EXDEV al mover adjuntos (`v1/controllers/widget/mensaje.controller.js`)

### Error en producción

```
EXDEV: cross-device link not permitted,
rename 'uploads/lnko4k4s9dg-1777907693971.pdf'
     -> '/app/uploads/files/2949-cxgayhasmpq/send/lnko4k4s9dg-1777907693971.pdf'
```

HTTP 500 al intentar enviar o recibir cualquier archivo adjunto en el endpoint `POST /widget/mensaje/crearSoulChat`.

### Causa raíz

La operación `fs.renameSync` es un `rename(2)` del kernel Linux: operación atómica que **solo funciona dentro del mismo dispositivo de bloque**. En la arquitectura Kubernetes del proyecto (definida en la Entrega 22/04/2026), el servicio corre en un único pod con:

| Ruta | Filesystem | Dispositivo |
|---|---|---|
| `uploads/` | Overlay ephemeral del pod (donde multer guarda el temp) | Device A |
| `uploads/files/` | PersistentVolumeClaim montado para persistir adjuntos entre redeployments | Device B |

Al hacer `renameSync` de Device A → Device B, Linux retorna `EXDEV`. El error nunca se manifestó en desarrollo local porque allí no hay PVC: todo vive en el mismo overlay filesystem.

La causa raíz aplica a los **tres puntos del controller** donde se movía el archivo temporal al destino final:

| Línea (antes del fix) | Función | Destino |
|---|---|---|
| 334 | `crearSoulChat` | `uploads/files/{idChat}-{remitente}/send/` |
| 901 | recepción de adjuntos | `uploads/files/{idChat}-{remitente}/received/` |
| 1174 | envío desde widget | `uploads/{idChatWeb}/` |

### Solución

Reemplazar `fs.renameSync` por `fs.copyFileSync` + `fs.unlinkSync`. `copyFileSync` lee y escribe byte a byte, funcionando entre cualquier par de filesystems. `unlinkSync` elimina el temporal tras la copia exitosa.

```js
// Antes — falla entre distintos dispositivos (EXDEV)
fs.renameSync(file.path, filePath);

// Después — funciona cross-device
fs.copyFileSync(file.path, filePath);
fs.unlinkSync(file.path);
```
